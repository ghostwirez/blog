Anti-Forensics 101: File Timestamp Manipulation

> Mar 6, 2026
> 6 min read
> ghostwirez
> NTFS · Windows · Linux

Timestamps are metadata — small pieces of information the operating system attaches to a file to record when it was created, last opened, or modified. They look authoritative. If a file says it was created in 2019, investigators assume it must have existed in 2019.

They're wrong. And those timestamps are incredibly easy to change.

// note
This post is for educational and defensive awareness purposes. Understanding how timestamp manipulation works is essential for both forensic examiners (detecting it) and red teamers (understanding detection surfaces).

What a Timestamp Actually Is

On Windows systems using NTFS — still the dominant filesystem in enterprise environments — a file doesn't have just one timestamp. It has two separate sets stored in the Master File Table (MFT), and they work in very different ways.

Attribute Visible in Explorer? Can user modify? Updated by
$STANDARD_INFORMATION ($SI) Yes Yes — no admin needed Userspace API calls
$FILE_NAME ($FN) No Requires kernel access Windows kernel only

This is the first major trap for attackers: if a tool only changes $SI timestamps, it creates a detectable inconsistency. The $SI might say a file was created in 2019, while $FN shows it was created last Tuesday.

// forensic flag
A mismatch between $SI and $FN is one of the highest-confidence indicators of timestamp tampering. Tools like Autopsy, Plaso, and commercial DFIR suites highlight this automatically.

The Toolbox

Windows — Metasploit Timestomp

The most commonly referenced tool. Modifies $SI attributes cleanly and can strip nanosecond precision. Default behavior does not touch $FN — a significant detection gap for skilled examiners.

# Inside a Meterpreter session
meterpreter > timestomp C:\\Windows\\Temp\\payload.exe -z "01/01/2020 08:00:00"
meterpreter > timestomp C:\\Windows\\Temp\\payload.exe -r  # randomize
bash

Windows — SetMace (Double Timestomping)

SetMace by jschicht addresses the $FN gap. It can modify both $SI and $FN attributes — a process known as double timestomping. Still not undetectable (USN journal, $LogFile, prefetch), but covers the obvious layer.

Windows — PowerShell (Native, No Binaries)

The quietest approach for simple cases — use what's already on the machine:

# Modify all three visible timestamps
$f = Get-Item "C:\Users\Public\payload.exe"
$f.CreationTime     = "01/01/2020 08:00:00"
$f.LastWriteTime    = "01/01/2020 08:00:00"
$f.LastAccessTime   = "01/01/2020 08:00:00"

# Or copy timestamps from a legitimate system file
$src = Get-Item "C:\Windows\System32\notepad.exe"
$tgt = Get-Item "C:\Users\Public\payload.exe"
$tgt.CreationTime  = $src.CreationTime
$tgt.LastWriteTime = $src.LastWriteTime
powershell

Operates at the Win32 API layer, so only $SI is modified. No external binary required — useful when dropping additional tooling is a risk.

Linux — touch

Linux ext4 timestamps: atime, mtime, ctime, and on newer kernels, crtime (birth time).

# Set access and modification times explicitly
touch -a -m -t 202001011200.00 maliciousfile

# Copy timestamps from a legitimate native file (blend in)
touch -r /usr/bin/curl maliciousfile
bash

The second form — cloning from a legitimate binary — is particularly effective. Instead of a suspicious fixed date, the file inherits the timestamp profile of a trusted native tool. Ctime cannot be directly modified via userspace. It updates whenever metadata changes, including when touch runs. This makes it a frequent tell on Linux systems.

Cross-Platform — Python

import os, time

ts = time.mktime(time.strptime("2020-01-01 12:00:00", "%Y-%m-%d %H:%M:%S"))
os.utime("/path/to/file", (ts, ts))  # (atime, mtime)
python

Three lines. Works anywhere Python is installed. The same ctime limitation from Linux applies, but for quick operations where deep forensic analysis is unlikely, this is sufficient.

The Nanosecond Problem

Windows NTFS stores timestamps with 100-nanosecond resolution. Real files almost never have perfectly rounded sub-second values. Most basic timestomping tools — including older Metasploit versions — zero out the nanosecond component.

// detection surface
A directory of thousands of files where one has a perfectly zeroed sub-second timestamp is trivially detectable by any examiner worth their rate. Use nTimetools (limbenjamin/nTimetools on GitHub) to randomize nanosecond values. 
# nTimestomp — set nanosecond-precision timestamps
nTimestomp.exe -f C:\payload.exe -c "2020-01-01 08:15:33.847291200"
cmd

The Counterintuitive Insight

Here's what most guides miss: clumsy timestomping makes analysis easier, not harder.

The MFT assigns sequence numbers in order of file allocation. A file showing a creation date of 2019 but holding an MFT sequence number wedged between files from last Thursday is an immediate contradiction — one no timestamp change can hide. The sequence reveals allocation order, not the claimed date.

Other corroborating sources that don't care about your timestamps:

ArtifactWhat it recordsAffected by timestomping?
MFT sequence numberAllocation orderNo
USN Journal / $LogFileFilesystem activity logNo
Prefetch filesExecution timestampsNo
Windows Event LogsProcess creation, etc.No
Shimcache / AmcacheExecution historyNo
$FN attributeKernel-level timestampsOnly via SetMace

Changing one layer while leaving the others untouched doesn't hide the file — it makes it stand out. Coherent manipulation across all evidence sources is extremely difficult and rarely seen outside of sophisticated, nation-state-level operations.

The Real Lesson

Timestamp manipulation exploits a cognitive bias: humans trust metadata more than they should. When we see Created: January 1, 2020, we instinctively classify the file as old, familiar, unrelated to the incident.

The best anti-forensics doesn't erase evidence. It creates evidence that appears believable. The best forensic work doesn't just look for evidence — it checks consistency across all evidence sources simultaneously.

Anyone can change a timestamp. Very few can change everything that remembers it.

// defensive notes
For blue teamers: enable $UsnJrnl on critical volumes, forward Windows Event Log 4663 (object access) to your SIEM, and baseline your most sensitive directories for $FN vs $SI discrepancies using tools like MFTECmd or Autopsy. Scheduled Shimcache exports also give you a longitudinal view of execution that timestamps can't touch.
